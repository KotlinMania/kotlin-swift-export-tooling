# ByteArray constructor repair

The original 2.4.20 constructor generator excludes all Kotlin arrays from the ordinary uninitialized-instance allocation path. It nevertheless exposes the public ByteArray initializers with fatalError bodies. The repair preserves the public signatures and uses a ByteArray-specific factory bridge: execute the typed Kotlin constructor once, create a retained external reference, then initialize the existing Swift wrapper from that reference. Ordinary constructors, other primitive arrays and the Native SDK binaries are unchanged.

The exact upstream source revision is `890ac1d94fdb80eb85f0eeb5be5e4352df987b2f`. `producer/byte-arrays/source-lock.json` pins the original file and patch. `repair.lock.json` pins eight baseline constructor classes, eleven candidate classes and five added classes. The inherited base, facade, inline helpers and two old anonymous classes remain byte-identical to the published parent. The portable build compares all non-debug attributes for the selected baseline classes, verifies excluded compiled deltas against the same source baseline, and resolves retained/new member descriptors, access and static flags against the complete worker closure.

The isolated Debug result at source `1559ef9` executed six named Swift cases once with no failures or skips: zero/empty initialization, exactly-once signed-byte initializer calls, Native alias mutation, Swift and Native weak-reference release, completed initializer-capture release, and a temporary constructor passed into Kotlin. Twelve product/test frontend records retain warnings as errors and macOS 15: eight dependency records use Swift 5, two authored records use Swift 6, and two generated-runner records have no explicit mode. Manifest compilation is recorded separately. Native bridge compilation, ARM64 static link and embed passed. One positive C process and six deliberately rejected size/index/receiver processes passed. All 40,932 prepared SDK files and generated inputs remained unchanged.

The first fixture attempt stopped before exporter execution because GC.collect required NativeRuntimeApi opt-in. The next attempt passed five Swift cases but checked release in the same frame as optional-array assertions. The accepted fixture returns that owning frame before checking both Swift and Native weak references; both clear. The original failures are retained, not rewritten as successes.

The rebuilt component `61ea24e3` also completed Native compilation/linking and all six Swift cases using the actual packaged helper-created SDK. Its local tool session reset after boundary compilation, so the original wrapper exit remains unknown. A separate recovery recompiled only the C probe, recorded all seven fresh process exits, and rechecked every frozen input, generated file and all 40,932 SDK files. No Native or Swift compilation was repeated during recovery. The final release-documentation update changes only the two embedded lock entries in the component; every class, runtime resource and other entry remains byte-identical. Exact-final hosted CI supplies a separate complete-run gate rather than relabeling the interrupted wrapper.

This is an isolated producer fixture, not Byteorder's three endian behaviors, another primitive-array implementation, arbitrary generic fidelity, actor safety, backward ABI compatibility or published Maven acceptance. The km.3 release must independently rebuild twice, validate the resulting distribution and actual packaged SDK helper, pass the producer’s real consumer fixtures and exact-final/main CI, then verify the immutable published Maven bytes. Byteorder subsequently validates its three unchanged endian cases through normal published-input selection.
